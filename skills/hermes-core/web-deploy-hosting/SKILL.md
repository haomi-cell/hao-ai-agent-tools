# Web Deploy via OAuth / Device Flow (no terminal user)

## Standing rules
- NEVER accept tokens, passwords, or API keys in chat — even if the user offers them. Decline and offer an OAuth/device-flow path instead. Credentials pasted in chat are treated as leaked; tell the user to rotate anything they already pasted.
- Deploy target: ask once (Netlify/Vercel/Cloudflare/Render), then execute end-to-end without re-asking. The user's recurring complaint in this class of task is being given options instead of the deploy being done.
- Preferred order for a chat-only user: 1) CLI OAuth authorize-link (one link they click in a browser), 2) manual hosting-dashboard import from their Git repo (guide via screenshots), 3) anything requiring a pasted token (avoid).
- Push code with `gh` CLI device flow first (`gh auth login --web`) so the repo exists on the user's account; hosters import straight from GitHub afterward.
- After deploy, verify the live URL yourself (curl, expect 200) before telling the user the site is online.

## Netlify CLI login technique
- `netlify login` blocks printing its authorize ticket. Capture it: run `script -qc 'netlify login' /tmp/nl.log` in the background (script writes output to a file readable while the process waits), then `grep -ao 'ticket=[a-f0-9]*' /tmp/nl.log | tail -1` and build `https://app.netlify.com/authorize?response_type=ticket&ticket=<id>`.
- Keep the login process alive across turns — agent kernel/session resets kill background processes, and an authorize granted to a dead ticket stores no token. Generate the ticket immediately before sending it; after the user says they authorized, re-check `~/.netlify/config.json` — if missing, generate a FRESH ticket (old ones expire) and have them click once more.
- One click = one ticket. Do not send a new link while a previous login process is still waiting; it confuses which ticket is live.
- Deploy: `netlify deploy --create-site --dir <dir> --functions <fn-dir> --site-name <name> --prod`. Static+functions layout for Netlify: publish dir holds HTML, functions dir holds serverless files; a `vercel.json` does not carry over (rewrites must be redone in `netlify.toml` or dashboard).

## Vercel CLI login (device flow)
- CLI is NOT preinstalled; `npm i -g vercel` puts the binary in the npm user prefix bin (find it with `ls ~/.openclaw-prefix/bin` here) — symlink into `~/.local/bin` and append that to PATH in `~/.bashrc` so future sessions find it.
- `vercel login` prints a device URL (`https://vercel.com/oauth/device?user_code=XXXX-XXXX`); run it backgrounded with `tee /tmp/vercel_login.log`, grep the URL, send it to the user, then poll the log for completion.
- To switch accounts, `vercel logout` first, then start a fresh login — a second `vercel login` while one is waiting double-counts device prompts.

## Vercel path (often the fastest for a GitHub user)
- If the repo is already pushed to the user's GitHub account, skip CLI auth entirely: have the user open vercel.com, log in with GitHub, 'Add New → Project' → import the repo → Deploy. Vercel auto-redeploys on every `git push`, so all later fixes are just push — no OAuth links, no tickets.
- Vercel serves the `public/` directory automatically; a rewrite `{"source":"/(*)","destination":"/public/$1"}` (or similar catch-all pointing into public/) shadows the static root and yields NOT_FOUND at `/`. Never rewrite paths into `/public/...` — instead add a single rewrite `{"source":"/","destination":"/<entry>.html"}` if the entry file is not index.html.
- After any routing fix, verify `curl -o /dev/null -w "%{http_code}"` for `/`, the static entry, and one API POST before reporting success; API responding with a JSON error body (not 404) means the function is wired correctly.

## Deploy chain: GitHub push → auto-deploy (Vercel + Cloudflare Pages)
- Stuck Vercel deploy symptom: repo content updated but `curl <site> | wc -c` differs from the repo file size for tens of minutes (backend 'Navigation' auto-commits of data.json also bury real user commits in history — check `git log --format='%h %ad %s' | grep -v Navigation` to find the user's actual edit). Fix without user action: push an empty commit (`git commit -q --allow-empty -m 'chore: deploy' && git push`) — it re-triggers the deploy; verify by byte-size compare afterward, allow several minutes for the build.
- Remote main changes constantly from the server itself (data.json auto-commits) — ALWAYS `git pull -q --rebase origin main` immediately before `git push`, or the push is rejected and a stale-tree push can conflict with the user's own GitHub-web edits. On conflict: abort, `git reset --hard origin/main`, re-apply the intended patch on the fresh tree (prefer the user's edits over agent edits when they collide).
- NEVER minify/whitespace-collapse the site's HTML for 'make it lighter' at this user's request — the inline CSS/JS is whitespace-sensitive and the result shipped broken visuals the user rejected and forced a full revert. Safe perf wins instead: cache headers on static assets (`express.static(..., { maxAge: '7d' })`) and, if ever attempted again, verify a visual regression BEFORE pushing.
- Multi-domain mirror (store on Vercel + full-function Cloudflare Pages mirror): point the pages.dev login button at the Vercel backend with OAuth `state=pages` so the callback returns the user to pages.dev, set the session cookie `sameSite:'none'`, add a CORS middleware allowing the pages.dev origin, and fetch with `credentials:'include'`. Verify CORS live with `curl -s -D - -H 'Origin: https://<site>.pages.dev' <backend>/api/...` expecting access-control-* headers — remember the Vercel runtime may be running the OLD deploy until the build lands, so a missing header right after push is not proof the code is wrong.

## Managing existing sites (CLI, after login)
- `netlify api listSites` maps site name → id → `build_settings.repo_url`; use this to find which site is linked to which repo before touching anything.
- Unlink a GitHub repo from a site (stop auto-deploy on push): `netlify api updateSite --data '{"site_id":"<id>","body":{"build_settings":{"stop_builds":true}}}'`. Verify with `getSite` — `stop_builds: true` is the success signal. The repo_url/repo_path fields themselves are read-only via the API; do not retry clearing them, stop_builds is the effective disconnect.
- A user's manual drag-and-drop or CLI-uploaded Netlify site does NOT track its GitHub repo: changing the repo changes nothing on the live site. Check which deploy path the site actually uses before assuming a push should update it.

## Other hosters: Supabase CLI login
- Install: `npm i -g supabase` (binary lands in the npm user prefix bin).
- `supabase login` waits for an Enter keypress first, so pipe/PTY it: run in a tmux session, `tmux send-keys Enter`, then capture the dashboard login URL from `tmux capture-pane`. The URL is printed split across lines — strip newlines before regex-matching.
- With `--no-browser`, after the user opens the dashboard link it shows a VERIFICATION CODE that must be typed into the waiting CLI prompt (read it from the same tmux pane and send it back); without `--no-browser` it tries to open a browser and hangs headless.
- When the user defers login ('nanti aja'), kill the pending login processes and just finish the install (symlink binaries into PATH, verify `--version`) — a waiting device-flow login held across turns dies with the agent session anyway.

## Cloudflare Pages (guided from the user's phone)
- Cloudflare's new dashboard hides Pages inside 'Compute → Workers & Pages → Create'; the direct URL `https://dash.cloudflare.com/?to=/:account/workers-and-pages/create/pages` skips the navigation hunt — hand the user this link when they ask 'which one?'.
- Distinguish the two deploy paths by their tell: a form showing 'Deploy command: npx wrangler deploy' is the Workers path and fails for a static repo (no wrangler.toml); the Pages path shows 'Build command' + 'Output directory' only. Steer static repos to Pages (Framework preset None, empty build command, output `/`).
- A static repo deploy gives a `<project>.pages.dev` domain and auto-redeploys on every git push, like Vercel.
- Env vars (e.g. OAuth client id/secret) go in the project's Settings → Variables and Secrets, added AFTER the first deploy, then re-deploy so they are read.

## Google OAuth (Sign in with Google) for a hosted site
- Free — never let the user follow the Google Cloud trial/billing prompt; OAuth Client IDs need no payment method.
- Phone walkthrough order: console.cloud.google.com → new project → APIs & Services → OAuth consent screen (User type EXTERNAL for public) → contact email → Create → Credentials → Create credentials → OAuth client ID → Web application.
- Fill Authorized JavaScript origins with the bare site origin and Authorized redirect URIs with the callback path the site's code actually uses (grep the deployed HTML/JS for `/auth/` paths first — guessing the path causes redirect_uri_mismatch).
- After the client is created, the user pastes the client id/secret as env vars on the hoster (names must match what the code reads, commonly GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET) and redeploys. A committed `.env` the Node app reads also works: fix env values by editing the file and pushing — verify what the live hoster actually reads before assuming the dashboard env is the source. Precedence rule for hand-rolled `.env` loaders (`if (!process.env[key]) process.env[key] = val`): hoster Environment Variables WIN over committed `.env` values, so the dashboard is always the override layer.
- Verify OAuth errors against the live redirect, not against assumptions: `curl -si https://<site>/auth/google | grep -oE 'client_id=[^&]+|redirect_uri=[^&]+'` shows exactly what the site sends; the Project Number in the user's Console screenshot must equal the client_id prefix. Wrong client id gives 'Error 401: invalid_client' at the Google authorize page; a valid client with an unregistered callback path gives 'Error 400: redirect_uri_mismatch' there too; invalid_client AFTER the user picks their account (backend error page) means the SECRET is wrong, not the id.
- Disambiguate which credential is bad in one shot, no user back-and-forth: `curl -s -X POST https://oauth2.googleapis.com/token -d 'code=test' -d 'client_id=<id>' -d 'client_secret=<secret>' -d 'redirect_uri=<callback>' -d 'grant_type=authorization_code'`. 'The provided client secret is invalid' confirms a bad secret instantly; this also re-verifies a secret transcribed from a screenshot without needing a live user login attempt.
- Google Cloud Console's new Auth Platform UI hides secret reset: the client EDIT form (pencil) has no reset button. Reset lives in the Clients list → tap the client NAME to open its detail panel → 'Client secrets' → reset icon. The credentials-list direct URL is `console.cloud.google.com/apis/credentials?project=<project-id>`.
- If the code supports BOTH direct-Google and Supabase-routed login, the redirect paths differ per flow (e.g. `/auth/google/callback` for direct, `<supabase-url>/auth/v1/callback` for routed): register BOTH variants of the site callback in the Google client, and transcribe client id/secret from screenshots character-by-character — one mistyped character reads as 'client not found'.
- If the reset path cannot be found (or after deletion is acceptable), fall back to DELETE the client and CREATE a new one with the same redirect URIs — a fresh client ships a fresh secret, avoiding the hidden reset entirely. Deleting the old client is confirmed live by the token endpoint returning `deleted_client`; a brand-new client may answer `not found` for a few minutes before propagating.
- In 'Testing' mode only registered test users can log in; PUBLISH APP on the consent screen makes it public (unverified-app warning remains until Google verification). New credential settings can take minutes to propagate.
- The user must do this themselves (their Google account) — guide step-by-step via screenshots; do not offer to drive their Google session. For a no-PC phone user, prefer handing the FULL direct URL (with project id / path filled in) over describing menu navigation — multi-level dashboards lose them; 'link ini' is the ask when they say 'yg mana'.

## Supabase auth setup (guided from the user's phone)
- Dashboard paths by direct link: `https://supabase.com/dashboard/project/<project-id>/auth/providers` (Google provider toggle), `.../settings/api` (Project URL + keys). Project ID comes from the project URL shown in the user's screenshot.
- Key types: `sb_publishable_...` is the PUBLIC key (safe in repo/chat) and the one frontend code reads; `sb_secret_...` is the secret — never let the user paste it into chat; if they do, tell them to Rotate it under API Keys before continuing.
- A project showing a 'NANO'/paused state or whose `<project-id>.supabase.co` domain fails DNS resolution is INACTIVE: it must be restored/resumed from the project card first — provider pages silently redirect back to the organizations list until it is active.
- During a live Supabase outage (banner 'investigating a technical issue' / status.supabase.com incidents), dashboard pages bounce to unrelated pages; do not debug the user's clicks — have them wait and retry after status clears.
- Google provider setup: Authentication → Sign In / Providers → Google → enable → paste the same OAuth Client ID (and secret if requested) from Google Console; the newer dashboard asks only 'Authorized Client IDs' (client id, no secret) — fill that field when it appears. then add redirect URI `<project-url>/auth/v1/callback` to the Google client. One Google client can serve multiple hosts — add one redirect URI per host (pages.dev, vercel.app, supabase callback) rather than replacing earlier ones.
- Code that supports both paths: `if client id+secret configured → redirect straight to Google; else if supabase configured → route via supabase /auth/v1/authorize?provider=google`. So a Supabase outage or skipped setup does NOT block login when direct Google creds exist — check which path the code prefers before telling the user Supabase is required.
- GitHub-as-database fallback (env `GITHUB_OWNER/REPO/DB_PATH/BRANCH/TOKEN` + a `data.json` in the repo) is a legitimate backup store when the user fears database limits; keep Supabase primary and GitHub secondary, never both writing simultaneously without understanding the code's read order. When the PRIMARY store is unreachable (Supabase paused/dead), disable it explicitly rather than letting the loader half-fall-back: a loader that tries the primary first returns intermittent empty data depending on timeout behavior. Set the primary's URL env to a placeholder the code treats as unset (hand-rolled loaders commonly guard on a `GANTI_`/empty prefix) so the fallback is deterministic — re-enable when the primary is restored.
- On Cloudflare Pages, `curl /<backend-path>` returning 200 does NOT prove a backend runs there — SPA/static hosting serves index.html for every path. Confirm by comparing the response body (look for the real page's title vs the static index) before claiming the backend is live; the backend for a static-pages deploy lives on the hoster that runs Node (e.g. Vercel), and the pages.dev login button points at it. One GitHub token in the hoster's env vars serves both — never duplicate it per hoster.
- Owner/admin UI pattern for member-tracking store apps: the backend already records every login (email, name, visits, saldo) if the code has an upsert-on-login — the missing piece is only an owner-gated view: add `/api/admin/members` gated by `ADMIN_EMAIL` env vs the session email, plus a profile-page button whose visibility is decided by probing that endpoint (403 = hide). Verify the helper names in the code (`loadDb(force)` vs an invented `readDb()`) before calling them — `node --check` catches the mistake pre-push.
- Do NOT gate the owner button's visibility on a client-side role check — a failed probe reads as 'button missing' and burns a debug round. But an ALWAYS-visible button confuses non-owner members too: they open the admin page, see zeros/empty lists, and report the feature 'broken'. Middle ground: render the button unconditionally but never show an empty data state to a non-owner — display the endpoint's error message verbatim (e.g. 'akses owner saja') instead of zeros, and surface fetch failures explicitly instead of leaving placeholders spinning.
- 'Rejected though I'm the owner' on an admin endpoint: diff the `ADMIN_EMAIL` value character-by-character against the email the user actually logs in with BEFORE touching code — a one-letter typo in the committed email produces a 403 identical to a wrong-logged-in-account. Ask the user to type their login email in chat and compare lowercased.
- Diagnosing 'registered users don't show up' in the member list: check storage reachability server-side first, not the UI. `curl https://<project-ref>.supabase.co` returning 000/NXDOMAIN while status.supabase.com is green means the PROJECT is paused — logins still work (direct-Google path) but writes go nowhere, so no data accumulates. Fix = user resumes the project from the dashboard card; logins made while paused are simply not recorded.
- A repo's `.gitignore` may exclude the fallback store filename (e.g. `data.json`); `git add -f` it — the GitHub-database backend reads it from the repo, so a gitignored file silently 404s.
- If the user insists their own API keys stay committed in a public `.env` after one warning, comply but state the risk exactly once and stop repeating it; continuing to lecture reads as nagging.
- To hand the user's GitHub token to a committed `.env` without the unblock dance: make the repo PRIVATE first (`gh api -X PATCH repos/<owner>/<repo> -F private=true` — one call, works with the user's own gh auth), then commit the token; push protection still fires on public repos only. GitHub has NO API to mint fine-grained tokens, so the only agent-obtainable credential is the session's full-scope `gh auth token` — that is safe to commit ONLY behind a private repo (on a public repo it hands the account to every reader). Note making the repo private kills raw/public file links for third parties (e.g. sharing with an external AI assistant) — re-share via zip instead.
- On PUBLIC repos, GitHub push protection BLOCKS any commit containing a real token (error GH013) — never put `GITHUB_TOKEN` in a committed `.env` there; use a placeholder in the repo and the real value in the hoster's Environment Variables. This also applies to OAuth client secrets (and even client IDs — the scanner pattern-matches both). To push anyway at the user's insistence: GitHub's rejection contains a per-secret `unblock-secret/<id>` URL; have the user open it, pick "I'll fix it later" (NOT 'false positive' — the secret is real), then "Allow me to expose this secret". EACH blocked pattern (id and secret) has its OWN unblock URL — expect one allow round per token, and the pending commit pushes unchanged after the last allow (`git push` again; 'nothing to commit' means the commit is already made and only the push was pending).

- A feature that calls a third-party API via a committed key (payment gateway, activator): when it fails, curl the upstream endpoint DIRECTLY with the committed key before debugging the app code — a provider 401 ('login diperlukan / invalid apikey') means the key expired or was revoked in the provider's panel, and the fix is the user replacing the key in `.env`/hoster env themselves (never in chat). App logic and user funds are usually unaffected: verify the code charges saldo only on success before reassuring the user.

## Repo hygiene: removing stale hosting links
- A URL shown under the repo name on GitHub lives in the repo's `homepage` field: clear it with `gh api -X PATCH repos/<owner>/<repo> -f homepage=''`. If it reappears, a hoster's GitHub App (e.g. Vercel integration) is rewriting it — remove the app at github.com/settings/installations.

## Pitfalls
- "Site not found" at the final URL before deploy completes is expected — the user opening the URL early does not mean deploy failed. Explain the order: authorize → deploy → URL goes live.
- Free-plan warning banners on the hosting dashboard (credits, team limits) are informational; static sites and functions still work free. Do not tell the user to upgrade.
- Capturing interactive CLI output via `/proc/<pid>/fd/1` usually fails (permission denied); use `script -qc '<cmd>' <logfile>` instead.
